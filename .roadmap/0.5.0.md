# Lunibee 0.5.x — the framework layer

**Theme:** everything a bot rewrites by hand on top of a library — command
registration and sync, routing buttons and menus, loading handlers, project
scaffolding — shipped as optional, first-party pieces. ZedBot today hand-rolls
each of these (Command class, CommandLoader, interaction routers, event binder);
0.5.0 lets a bot delete that code.

**Target:** 0.5.0, then 0.5.x patches. Branch: `dev`.

**Principle:** opt-in packages on top of the core. `lunibee` without them stays a
plain library; nothing here is required to connect, send or cache.

---

## Step 1 — `@lunibee/commands`: one command definition, every surface

1. [ ] `defineCommand({ data: CreateSlashCommand | CreateContextMenuCommand, run, autocomplete?,
   prefix?: { aliases, args } })` — one object serves slash, context menu and (optionally) prefix.
2. [ ] Prefix arguments derived from the slash options via `argsFromCommandOptions` and
   `parsePrefixArgs` (0.2.1); free-text options take the rest of the line.
3. [ ] Checks as composable guards: `guildOnly`, `ownerOnly(ids)`, `permissions(bits)` (checked
   server-side), `botPermissions(bits)`, `cooldown({ per: "user" | "guild", ms })` backed by a
   bounded TTL collection.
4. [ ] `CommandRegistry.load(dir)` (file-based, like the CLI layout) and `register(command)`.
5. [ ] `registry.sync(client, { guildId? })`: diff local vs remote commands and only PUT when
   changed (hash stored in memory; no needless global writes on every restart).
6. [ ] Error boundary: thrown errors reply with a safe message, log the error with command name,
   guild and user ids, never the stack to users.
7. [ ] Per-guild enable/disable hook (`isEnabled(guildId, command)`) so bots can plug in module
   switches like ZedBot's `/config` without forking the dispatcher.
8. [ ] Tests: dispatch for each surface, guards, cooldown expiry, sync diffing.

## Step 2 — `@lunibee/components`: persistent component routing

1. [ ] `router.button("ticket:close:{ticketId}", handler)` — custom-id patterns with typed params,
   parsed and length-checked (100-char Discord limit enforced at build time).
2. [ ] Same for selects (`router.select`), modals (`router.modal`) with typed field access.
3. [ ] Works across restarts (no in-memory collector needed); collectors remain for short flows.
4. [ ] Per-route guards (same guard primitives as commands) re-checked on every click.
5. [ ] Short-lived state helper: `router.state<T>({ ttl, maxSize })` for multi-step flows
   (imports, wizards) keyed by user/guild, bounded.
6. [ ] Tests: pattern matching, param validation, unknown ids ignored, guard refusal.

## Step 3 — `@lunibee/handlers`: events from files

1. [ ] Runtime counterpart of the CLI binder: `loadEvents(client, dir)` with the
   `src/events/<event>/<name>.ts` layout and `handler(client, ...args)`.
2. [ ] Validates folder names against `ClientEvent`; unknown folders are reported, not ignored.
3. [ ] Hot reload in development (`bun --watch` friendly): unbind old listeners before rebinding.
4. [ ] The CLI keeps generating a static binder for production (no dynamic imports).

## Step 4 — CLI: projects, not just files

1. [ ] `bunx lunibee create app <name>` (via `@lunibee/create`): templates `minimal`, `commands`
   (with `@lunibee/commands`), `sharded` (ClusterManager + IPC bus), `mongo` (config cache pattern).
2. [ ] `lunibee create command <name> [--context user|message] [--prefix]` using `defineCommand`.
3. [ ] `lunibee create component <pattern>` producing a router entry.
4. [ ] `lunibee sync commands [--guild id]` calling the registry sync.
5. [ ] `lunibee doctor` checks intents vs used events (e.g. `guildMemberAdd` needs GUILD_MEMBERS),
   token format (never printed), `.env` git-ignored.
6. [ ] Tests run the CLI in a temp dir for each subcommand.

## Step 5 — Plugins

1. [ ] `client.use(plugin)` with a small contract: `name`, `setup(client)`, `teardown()`.
2. [ ] Lifecycle ordering with the client (setup before login, teardown on destroy).
3. [ ] First-party examples: `@lunibee/plugin-logger` (structured logs with redaction),
   `@lunibee/plugin-metrics` (see step 6).
4. [ ] Plugins cannot touch private internals: they get the public client only.

## Step 6 — Observability

1. [ ] Metrics hooks on REST (latency, 429s, bucket waits), Gateway (latency, reconnects,
   resumes, dispatch rate), caches (size, hit/miss, evictions).
2. [ ] Pluggable sink: Prometheus text endpoint helper and an OpenTelemetry adapter (optional deps).
3. [ ] Structured debug events with token/authorization redaction guaranteed by tests.

## Step 7 — Caching policies

1. [ ] Per-cache options on `ClientOptions.cache`: `{ members: { maxSize, ttl, keep: (m) => boolean } }`
   for members, messages, presences, voice states, threads.
2. [ ] Sweepers run on one unref'd timer; documented memory per guild at each preset
   (`minimal`, `default`, `full`).
3. [ ] Tests: eviction, keep-predicate, sweeper cleanup on destroy.

## Step 8 — Localization helpers

1. [ ] `localize(key, locale, vars)` with fallback chain; builders accept `name_localizations` /
   `description_localizations` from a locale map.
2. [ ] `interaction.locale` / `guildLocale` helpers.

## Step 9 — Documentation and examples

1. [ ] `examples/complete-bot`: slash + prefix + context menus, components router, moderation,
   sharding, Mongo config cache — the sample bot ROADMAP.md asks for at 0.9.0, started here.
2. [ ] Guides: Commands, Components, Handlers, Plugins, Observability, Caching.
3. [ ] Migration guide "from a hand-rolled command handler" (ZedBot as the worked example).

## Step 10 — Release 0.5.0

1. [ ] Mark new packages `@experimental` where the API is not settled; list them in ROADMAP.md.
2. [ ] Release checklist below; tag; announcement; ZedBot migrates its Command/CommandLoader
   and routers to the new packages as the adoption test.

## After 0.5.x

0.9.0 API freeze (mark every export public/internal/experimental, resolve duplicate names,
upgrade guide to 1.0), then 1.0.0 — see ROADMAP.md.

## Release checklist

- [ ] Root and workspace package versions correct (new packages start at 0.5.0)
- [ ] Changelog updated; breaking changes (none to core) documented
- [ ] Upgrade guide updated
- [ ] Examples use the release version (complete-bot runs)
- [ ] P0/P1 resolved and verified; P2/P3 resolved or tracked
- [ ] `check:deps` (new packages placed in the layer graph), API audit, prettier, typecheck,
      tests + coverage
- [ ] Production build, DTS build, docs build, generated API docs
- [ ] Final smoke test: `bunx lunibee create app` → run → slash command responds
