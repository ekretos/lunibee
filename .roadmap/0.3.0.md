# Lunibee 0.3.x — complete the platform

**Theme:** close the gaps a production bot hits before voice or a framework layer
matter: typed payloads, sharding that works across processes, the remaining
Gateway seams, and full coverage of Discord's current API.

**Target:** 0.3.0, then 0.3.x patches. Branch: `dev`.

**Breaking changes allowed:** removing the APIs deprecated in 0.2.x (Step 0).
Otherwise none to runtime behaviour. Type narrowing (typed
payloads replacing `Record<string, unknown>`) may surface compile errors in
callers passing invalid shapes; unknown keys stay allowed so valid code compiles.

---

## Step 1 — Typed message and interaction payloads

`MessagePayload` and `Buildable<T>` already exist in `@lunibee/types` (0.2.3). Typing the send
and reply signatures with them was deferred from 0.2.3 because it breaks callers that declare
`embeds: unknown[]` (16 new errors in ZedBot); do it here, with that listed under breaking changes.

1. [ ] Define `MessageCreateOptions` in `packages/types`: `content`, `embeds`, `components`,
   `files`, `allowed_mentions`, `flags`, `poll`, `message_reference`, `sticker_ids`, `tts`,
   `enforce_nonce`/`nonce`, plus `[key: string]: unknown` for new Discord fields.
2. [ ] `MessageEditOptions`, `InteractionReplyOptions` (adds `ephemeral`, `withResponse`),
   `InteractionUpdateOptions`, `FollowUpOptions`, `WebhookExecuteOptions` built from it.
3. [ ] Accept builders anywhere an embed/component payload is accepted (`toJSON()` resolved in
   one place: `resolvePayload()` in core).
4. [ ] Replace `Record<string, unknown>` in `channels.send/edit`, `message.reply/edit`,
   interaction reply/editReply/followUp/update, webhooks.
5. [ ] Type tests (`tests/types/*.test-d.ts` via `tsc --noEmit`) for valid and invalid shapes.
6. [ ] Docs: "Sending messages" guide rewritten around the typed options.

## Step 3 — Cross-process `ShardBus`

`BroadcastChannel` does not cross `fork()`ed clusters, so cross-cluster messaging is broken
(docs/audits/sharding-report.md, gap 1).

1. [ ] Define a `ShardBusTransport` interface: `post(message)`, `onMessage(listener)`, `close()`.
2. [ ] `BroadcastChannelTransport` (today's behaviour, single process) and `IpcTransport`
   (`child.send()` / `process.on("message")`, parent relays between children).
3. [ ] `ClusterManager` selects `IpcTransport` automatically when it forks; manual override option.
4. [ ] Keep `broadcast`, `send`, `request`/`respond` semantics; add request timeouts and a bounded
   pending-request map (TTL + max size).
5. [ ] Surface handler rejections as `error` events (never swallowed).
6. [ ] Tests: two forked workers exchanging broadcast and request/response; timeout; worker death
   mid-request rejects the pending promise.
7. [ ] Docs: sharding guide with the process topology diagram.

## Step 4 — IDENTIFY concurrency (`max_concurrency`)

1. [ ] Read `session_start_limit.max_concurrency` and `remaining` from `/gateway/bot`
   (one shared `fetchGatewayBot()` helper replacing the duplicated `fetchRecommendedShardCount`,
   with the real library version in `User-Agent`).
2. [ ] Group shards into buckets `shardId % max_concurrency`; start one bucket per 5 seconds.
3. [ ] Refuse to start (clear error) when `remaining` session starts would be exhausted.
4. [ ] Store the total shard count so `getShardIdForGuild` stays correct during reshards.
5. [ ] Aggregated events on `ShardManager`: `shardReady`, `shardDisconnect`, `shardResume`, `shardError`.
6. [ ] Tests with a fake clock for bucket timing and the session-limit refusal.

4. [ ] No public API change beyond the new option; existing tests pass unchanged; new unit tests

## Step 5b — Liveness hardening (after the 0.2.2 zombie fix)

1. [ ] Soak test in CI: a fake Gateway sending sparse traffic for 30 simulated minutes per shard;
   assert zero reconnects on a healthy link and exactly one on a silenced one.
2. [ ] Expose `gateway.health()` (last ACK latency, silentFor, reconnect count) for bots and the
   0.5.0 metrics hooks.
3. [ ] Rate-limit reconnect storms: if a shard reconnects more than N times in a window, back off
   exponentially and emit a `shardUnstable` event instead of looping.

## Step 6 — `ShardSupervisor` (Stage 1C)

3. [ ] Tests for crash loops and the give-up threshold.

## Step 7 — REST: concurrent buckets on by default (REST-003 follow-up)

REST-003 shipped in 0.2.x as the opt-in `concurrentBuckets` option.

1. [ ] Benchmark sequential vs concurrent against a fake server with realistic limits (`benchmarks/`).
2. [ ] Soak test: 10k requests across shared buckets with no 429 beyond Discord's global slack.
3. [ ] If both pass, make `concurrentBuckets` the default; keep `concurrentBuckets: false` for
   callers relying on strict per-bucket ordering; changelog "Changed" + upgrade note.

## Step 9b — Performance targets (from BUN.md, 2026-09-30)

Baseline: `scripts/bench-runtime.mjs`, medians in `docs/perf/runtime-2026-09-30.json`,
write-up in [BUN.md](../BUN.md).

1. [ ] Collection scans: stop copying with `[...this.values()]` in `at`, `keyAt`, `random`,
   `randomKey`, `array`, `keyArray`; walk once (stop at the index; reservoir-pick for random).
   Target on Bun 1.4: `at` / `random` ≤ 2.5 µs at 1,000 items (Node today ~2.3 µs, Bun ~11 µs).
2. [ ] `filter` / `clone` / `find` / `each`: skip the purge-per-call overhead when no entry has
   a TTL. Target: `filter` ≤ 20 µs at 1,000 items on Bun 1.4 (today ~37 µs; Node ~19 µs).
3. [ ] Cheap pass-through events where Node is 1.3–2.6× faster (`CHANNEL_CREATE`,
   entitlements, reactions, `VOICE_SERVER_UPDATE`, `INTERACTION_CREATE`): profile on Bun and
   remove per-event allocations.
4. [ ] Hold the wins: `MESSAGE_CREATE` ≤ 5 µs, `GUILD_CREATE` (50 members) ≤ 120 µs, builders
   geometric mean ≤ 800 ns on Bun 1.4.
5. [ ] `bench:compare`: run `runtime.mjs --json`, compare with the committed baseline, warn
   (later fail) on a > 15% regression; run in CI on Bun 1.4.
6. [ ] Make Bun 1.4.x the documented minimum and the CI runtime; keep Node 22 as
   works-but-unsupported (the built package runs the whole benchmark on it without errors).
