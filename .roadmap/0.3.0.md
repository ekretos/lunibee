# Lunibee 0.3.x — complete the platform

**Theme:** close the gaps a production bot hits before voice or a framework layer
matter: typed payloads, sharding that works across processes, the remaining
Gateway seams, and full coverage of Discord's current API.

**Target:** 0.3.0, then 0.3.x patches. Branch: `dev`.

**Breaking changes allowed:** removing the APIs deprecated in 0.2.x (Step 0), and the
workflow change in Step 0b (old API kept as deprecated aliases).
Otherwise none to runtime behaviour. Type narrowing (typed
payloads replacing `Record<string, unknown>`) may surface compile errors in
callers passing invalid shapes; unknown keys stay allowed so valid code compiles.

## Step 0b — A workflow of its own (breaking; direction chosen, design under review)

Lunibee reads too much like discord.js. Give it its own shape without breaking
existing bots in one jump: the old API stays as `@deprecated` aliases (removed in
0.4.0), the new one is what docs and examples use. **Pick one direction before
starting; the options are not exclusive.**

- **A. Renamed surface.** Same objects, different entry points: `client.guild(id)`,
  `client.channel(id)` instead of `client.guilds.fetch()` and friends; managers
  become the escape hatch, not the front door.
- **B. Definitions, not listeners.** `defineEvent()` / `defineCommand()` objects keep a
  command, its options and its handler together; `lunibee sync` wires them. Builds on
  the existing handler files and `lunibee create handler`.
- **C. Result-style errors.** Methods return `{ ok, value, error }` (or a `.try()`
  variant) instead of throwing.

Whatever is chosen:

1. [~] Design written in [`docs/lunibee-3-workflow.md`](../docs/lunibee-3-workflow.md): handles with
   `peek` / `get` / `fetch`, a chained `bot.api`, channel `kind`, `command()` with typed
   `option.*` (slash, prefix or both), CLI `create command --slash|--prefix|--both`. Names and open questions
   agreed (see its Decisions section).
2. [~] Implement behind the existing API; add `@deprecated` to what it replaces. Order in the design
   doc: (1) [x] handles, (2) [x] channel kinds, (3) [x] `command()` / `option.*` / `bot.commands`,
   (4) [x] `bot.api`, (5) [x] CLI flags, (6) [x] docs, Quick Start, example and Upgrading moved (no text-level migrate rewrites: unprovable).
3. [ ] `lunibee migrate` rewrites the old calls (it already does this for the 0.2.2 names).
4. [ ] Update the Quick Start, recipes and `examples/` to the new workflow only.
5. [ ] Upgrading page: a before/after table; changelog "Changed" entry. Not allowed to
   slip into a patch release.

4. [x] Keep `broadcast`, `send`, `request`/`respond` semantics; add request timeouts and a bounded

## Step 9b — Performance targets (from BUN.md, 2026-09-30)

Baseline: `scripts/bench-runtime.mjs`, medians in `docs/perf/runtime-2026-09-30.json`,
write-up in [BUN.md](../BUN.md).

1. [~] Collection scans (`random` / `randomKey` without an amount are done in 0.2.4): stop copying with `[...this.values()]` in `at`, `keyAt`,
   `array`, `keyArray`; walk once (stop at the index; reservoir-pick for random).
   Target on Bun 1.4: `at` / `random` ≤ 2.5 µs at 1,000 items (Node today ~2.3 µs, Bun ~11 µs).
2. [ ] `filter` / `clone` / `find` / `each`: skip the purge-per-call overhead when no entry has
   a TTL. Target: `filter` ≤ 20 µs at 1,000 items on Bun 1.4 (today ~37 µs; Node ~19 µs).
3. [ ] Cheap pass-through events where Node is 1.3–2.6× faster (`CHANNEL_CREATE`,
   entitlements, reactions, `VOICE_SERVER_UPDATE`, `INTERACTION_CREATE`): profile on Bun and
   remove per-event allocations.
4. [ ] Hold the wins: `MESSAGE_CREATE` ≤ 5 µs, `GUILD_CREATE` (50 members) ≤ 120 µs, builders
   geometric mean ≤ 800 ns on Bun 1.4.
5. [ ] `bench:compare`: run `runtime.mjs --json`, compare with the committed baseline, warn
   (later fail) on a > 15% regression; run in CI on Bun 1.4.
6. [x] **Lazy retention state (done in 0.2.4).** A `Collection` without `ttl` or `maxSize` no
   longer allocates its expiry map, recency list, heap and stats object: ~360 → ~20 bytes per
   empty collection (Bun, 100k instances), the same as `Map` / discord.js. They are created
   with the first `ttl` / `maxSize`, or the first `set()` that passes its own TTL.
7. [~] Collection `ttl` and `maxSize` writes. Done in 0.2.4: one policy record per key serves the
   policy map, the recency list and the expiry heap (a write allocates once and touches one
   extra hash entry, not two); a heap that sifts without swaps; no timer re-arm while an earlier
   one is armed; no lookups to find out a new key is new; one-step LRU eviction; `get()` does
   one policy lookup and one `Date.now()`. A fuzz test (`tests/collection.model.test.ts`)
   checks the collection against a plain model of its documented behaviour. Measured
   2026-10-07 (Bun, 200k keys, GC between runs, best of 15, ns per `set`; this machine varies
   ±20%): plain ~200-230; `ttl` ~770-840; `maxSize` evicting ~770-930; `ttl` + `maxSize`
   ~1,000-1,115 (was ~1,700-1,900 before 0.2.4 work, ~1,450 after the first pass). The floor
   for one policy map is a hash write plus an allocation, ~600 ns on Bun, so "≤ 2× plain `set`"
   is not reachable. Target: `ttl` or `maxSize` `set` ≤ 4× plain, both ≤ 5×.
8. [x] **`benchmarks/collection.ts` compares with discord.js (done in 0.2.4).** Rows for `set`, `get`,
   `filter`, `find`, `random`, `at` and shallow bytes per empty instance; contenders take turns
   within each round and the best run is kept, so figures are stable on a busy machine.
   Measured 2026-10-07 (Bun, best of 15), ratios against discord.js: plain `set` 1.3-1.4×;
   plain `get` 1.2×; `filter` / `find` / `at` equal; `random` 8× faster (no copy). With
   `ttl` or `maxSize`: `set` 4.7-5.7×, `get` 2-3.3×. Empty collection: 35 B (Map and
   discord.js: 32 B).
   **`get` speed-up (done in 0.2.4):** a policy entry keeps a copy of its value, so a read of
   a `ttl` / `maxSize` entry is one lookup instead of two; plain `get` calls `Map.prototype.get`
   directly. `get` with `ttl` 270-280 → 190-210 ns, with `ttl` + `maxSize` 320-340 → 190-215 ns,
   with `maxSize` 175-185 → 120-150 ns, plain 90-100 → 85-93 ns (Bun, 100k keys, best of 40).
   What is left: plain `set` and `get` pay for being a JS override of a native `Map` method
   (~15-60 ns); `Date.now()` costs ~37 ns of every TTL `get`.
9. [x] **`Cache` on the recency list (done in 0.2.4).** `Cache` wraps a `Collection` with
   `slide: false`. Bounded `set` + `get` at 100k entries: ~17 µs → ~1.1 µs (ttl + maxSize
   ~16.9 µs → ~2.5 µs). `values()` / `entries()` now follow first-insertion order.
10. [x] **Collection API gaps against discord.js (done in 0.2.4).** `ensure(key, factory, ttl?)`,
   `random(amount)` / `randomKey(amount)`, `findLast` / `findLastKey`, `Symbol.species`,
   `mapValues`, `reduceRight`, `concat`, `equals`, `merge`, `symmetricDifference`,
   `combineEntries`, `groupBy`, `toSorted` / `toReversed` and `ReadonlyCollection`, each with
   tests and a reference-page entry. Lunibee keeps its own `get()` (slides TTL, promotes) and
   `peek()` semantics. In-place `sort()` / `reverse()` are deliberately not provided.
11. [ ] Make Bun 1.4.x the documented minimum and the CI runtime; keep Node 22 as
   works-but-unsupported (the built package runs the whole benchmark on it without errors).
