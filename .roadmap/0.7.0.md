# Lunibee 0.7.x — Discord API coverage and fully typed payloads

**Theme:** close the distance between Lunibee and Discord's current API, and
finish the typed-payload work 1.0 requires (no `Record<string, unknown>` in
public message or interaction option types).

**Target:** 0.7.0, then 0.7.x patches. Branch: `dev`.

**Principle:** each Discord feature ships with its structure, builder (where Discord has a
payload to build), REST route coverage, Gateway events and cache handling, or is listed as
"not planned" with the reason. The REST coverage audit (`audit:coverage`) stays at 100%.

---

## Step 1 — Coverage audit against Discord's current docs

1. [ ] Re-run the resource audit from 0.3.1 against Discord's API docs as of the start of the line:
   routes, Gateway events, payload fields, component types.
2. [ ] Every gap becomes a step below or a "not planned" row in the docs.

## Step 2 — User-installable apps and interaction contexts

1. [ ] `integration_types` and `contexts` on command builders and in sync; `interaction.context`,
   `authorizing_integration_owners`, `app_permissions` typed.
2. [ ] Commands that run outside guilds (user installs, DMs, group DMs) work with `command()` and
   `defineCommand`; guards that need a guild say so.
3. [ ] `lunibee init` asks about install type alongside the command type.

## Step 3 — Monetization

1. [ ] SKUs, entitlements and subscriptions: structures, REST, Gateway events and cache.
2. [ ] `interaction.entitlements` helpers; the premium button component.
3. [ ] Test entitlements in the testing package.

## Step 4 — Remaining resources

1. [ ] Soundboard sounds (send, list, Gateway events), application emojis, polls (create, end,
   results, vote events typed), guild onboarding, and anything else Step 1 finds.
2. [ ] Components v2: every component type and its limits validated in builders.

## Step 5 — Typed payloads everywhere (1.0 exit criterion)

1. [ ] Replace each remaining `Record<string, unknown>` in public message, edit, reply, follow-up,
   modal and webhook option types with an interface; unknown keys stay allowed through one
   documented escape hatch (`raw`), so new Discord fields still pass.
2. [ ] The API audit fails on a new `Record<string, unknown>` in a public option type.
3. [ ] Type tests (`expectTypeOf`) for every option interface.

## Step 6 — Voice receiving

1. [ ] `VoiceReceiver` gets a decoded-PCM stream helper (Opus decode per user), silence handling and
   a bounded jitter buffer; still marked `@experimental` if 0.6.0's smoke test does not cover it.
2. [ ] Recorded-session replay covers receiving.

## Step 7 — Release 0.7.0

1. [ ] Upgrade guide for any type that became stricter.
2. [ ] Release checklist below; tag; announcement.

## Release checklist

- [ ] Root and workspace package versions correct (0.7.0)
- [ ] Changelog and upgrade guide updated
- [ ] P0/P1 resolved and verified; P2/P3 resolved or tracked
- [ ] `check:deps`, API audit, `audit:coverage` at 100%, prettier, typecheck, tests + coverage
- [ ] Production build, DTS build, docs build, generated API docs
- [ ] Final smoke test: a user-installed command answers in a DM
