When a Discord bot joins more than **2,500 guilds**, Discord enforces Gateway Sharding. Each shard maintains its own independent WebSocket connection and handles a fraction of the bot's total servers.

---

## How Shard Allocation Works

Discord distributes guilds across shards using a deterministic snowflake formula:

`$$\text{Shard ID} = (\text{Guild ID} \gg 22) \pmod{\text{Total Shards}}$$`

Lunibee handles this calculation automatically via `manager.getShardIdForGuild(guildId)`.

import { ShardManager, IntentBits } from "lunibee";

## Cross-Shard Messaging with `ShardBus`

`ShardBus` passes messages between shards. Inside one process it uses a named `BroadcastChannel`; in a cluster forked by `ClusterManager` it uses IPC automatically (0.3.0), because a `BroadcastChannel` does not cross `fork()`ed processes.

```text
ClusterManager (parent)
 ├─ cluster 0 ── shards 0, 2 ──┐  worker.send(frame)
 ├─ cluster 1 ── shards 1, 3 ──┼─▶ parent relays the frame to every other cluster
 └─ cluster 2 ── shards 4    ──┘  and, when a cluster exits, tells the others which shards are gone
```

Your code does not change: `new ShardBus(shardId, "my-bot")` picks the transport. Pass `{ transport }` (a `ShardBusTransport`: `post`, `onMessage`, `close`) to override it. A request to a shard whose cluster dies rejects at once instead of waiting for its timeout, `maxPending` (10,000 by default) bounds the requests waiting for replies, and an error thrown by a handler reaches `onError` listeners, or becomes a process warning (`LUNIBEE_SHARD_BUS_ERROR`) when there are none.

```ts
import { ShardBus } from "lunibee";

const bus = new ShardBus(shardId, "my-bot");

// Fire-and-forget
bus.on("reload", (message) => reloadConfig(message.data));
bus.broadcast("reload", { section: "commands" });

// Errors thrown or rejected by handlers
bus.onError((error, message) => console.error(message.type, error));
```

### Queries across shards

`respond()` answers requests. `request()` asks one shard; `broadcastRequest()` asks every
other shard and collects replies until `expected` arrive or the timeout passes. This
covers discord.js's `broadcastEval` use cases without sending code to be evaluated.

```ts
bus.respond("guildCount", () => client.guilds.cache.size);

const one = await bus.request<number>(1, "guildCount", null);      // throws on timeout
const all = await bus.broadcastRequest<number>("guildCount", null, {
  expected: totalShards - 1,
  timeoutMs: 5_000,
});
const total = all.reduce((sum, r) => sum + (r.result ?? 0), 0);
```

`ShardingManager` is an alias of `ShardManager`.

## Events, buckets and the start limit (0.3.0)

`ShardManager` re-emits what its shards do, each with the shard id first: `shardReady`, `shardDisconnect` (with `{ code, action }`), `shardResume`, `shardError` and `shardUnstable`.

```ts
manager.on("shardReady", (id) => console.log(`shard ${id} ready`));
manager.on("shardDisconnect", (id, { code }) => console.warn(`shard ${id} closed: ${code}`));
```

Discord rate-limits IDENTIFY per `shard_id % max_concurrency`. Lunibee groups the shards that need a connection by that key and starts the next shard of every bucket together, then waits `spawnDelay` (5 s) before the next round. It refuses to start, with a clear error, when `/gateway/bot` reports fewer remaining session starts than shards to connect. `getShardIdForGuild()` keeps using the shard count of the current set while a reshard has no shards, and `fetchGatewayBot(token)` is the one helper both managers use to read `/gateway/bot`.

## Startup Pacing and Health

With `shardCount: "auto"`, the manager reads `/gateway/bot` and starts shards
in rounds of Discord's `max_concurrency` (override with `maxConcurrency`),
waiting `spawnDelay` between rounds. It refuses to start more shards than the
remaining session-start budget and tells you when it resets.

```ts
const manager = new ShardManager({ token, intents, shardCount: "auto" });
await manager.connect();
manager.health(); // [{ id, state, ping }, ...]
```

Rounds are spaced from the moment each shard sends IDENTIFY/RESUME, not from
socket open (`handshakeTimeout`, default 15 s, bounds that wait). A
`maxConcurrency` override is capped at Discord's value. Shards that are
already connected do not count against the session start limit, and a
too-small budget never tears down running shards.

## Restarting crashed clusters

`ClusterManager` re-forks a cluster that exits. By default every crash is restarted after `restartDelay`. For a crash loop, add a supervisor policy:

```ts
new ClusterManager({
  token, script: "./bot.js",
  supervisor: { restartDelay: 1000, backoff: 2, maxDelay: 60_000, jitter: 0.2, maxRestarts: 5, window: 60_000 },
  onGiveUp: (cluster) => console.error(`cluster ${cluster.id} keeps crashing`),
});
```

Each crash inside `window` doubles the delay (up to `maxDelay`, plus jitter); more than `maxRestarts` crashes inside `window` stops restarting that cluster and calls `onGiveUp`. A cluster that stays up for a full `window` starts over. `ShardSupervisor` is exported for custom managers.
